# ADR: RequestContext and RequestIdentity

**Date:** 2026-07-14  
**Status:** Approved; Policy Kernel design gate passed on 2026-07-14  
**Decision owner:** Policy Kernel design gate  
**Scope:** Interface and lifecycle design only.

## 1. Context

CodexPro currently accepts requests through STDIO and Streamable HTTP. HTTP may authenticate with the personal query-token compatibility flow or a Bearer token. MCP transport sessions exist, but current workspaces are service-level objects and are not yet bound to a stable request identity.

Phase 2A needs one identity and context interface that works before OAuth 2.1 and can accept OAuth subject/scopes later without introducing a second identity system.

The design must distinguish:

- transport security from authorization;
- a credential from a human user;
- a transport session from a long-lived identity;
- a stable canonical workspace key from a session-bound workspace handle;
- Tool Surface selection from permission policy;
- a policy snapshot from a mutable saved profile.

## 2. Decision

CodexPro will create one immutable `RequestContextV1` for every request entering the central tool wrapper. The context contains a normalized `RequestIdentityV1`, transport facts, workspace binding when applicable, selected runtime and permission profiles, policy revision, and grant revision.

Raw credentials never enter `RequestContextV1`.

## 3. RequestIdentityV1

```ts
interface RequestIdentityV1 {
  schemaVersion: 1;
  kind:
    | "local_process"
    | "loopback_unauthenticated"
    | "shared_secret_query"
    | "shared_secret_bearer"
    | "oauth_subject";
  authenticationMode:
    | "stdio"
    | "loopback_none"
    | "query_token"
    | "bearer"
    | "oauth2";
  credentialRef: string | null;
  subject: string | null;
  scopes: string[];
  assuranceLevel: "local" | "low" | "shared_secret" | "strong";
}
```

### 3.1 Credential reference

`credentialRef` is a safe local identifier, not a credential. It is generated from the credential using an application-local secret and a domain-separated HMAC. It must:

- be stable for the same credential within the same CodexPro installation;
- differ across installations even when the raw credential is the same;
- be non-reversible from logs or audit records;
- use a bounded public representation such as `cred_<base32-prefix>`;
- never be generated by directly truncating a raw Token hash without a local secret.

If no credential exists, `credentialRef` is `null`.

### 3.2 Subject

`subject` is only populated when the authentication mechanism provides a genuine stable subject, such as an OAuth subject in Phase 8. Query and Bearer static-token modes do not invent a human subject.

### 3.3 Scope semantics

Scopes express capability categories only. They do not contain paths, domains, commands, repositories, remotes, or workspace identifiers. The V1 set is:

```text
workspace:open
filesystem:read
filesystem:write
git:read
git:write
git:remote-write
shell:verify
shell:execute
process:manage
network:connect
audit:read
admin:profile
admin:credentials
```

Unknown scopes are rejected by strict validation. A future schema version may add scopes without changing the meaning of V1 names.

## 4. Transport identity mapping

### 4.1 STDIO

```text
kind = local_process
authenticationMode = stdio
credentialRef = null
subject = null
assuranceLevel = local
```

Scopes come from the deployment identity configuration. STDIO is trusted only as the local process connection; it is not permission to escape allowed roots, hard policy, or the selected Permission Profile.

### 4.2 Explicit unauthenticated loopback

This identity exists only when the existing reviewed loopback no-token override is explicitly enabled.

```text
kind = loopback_unauthenticated
authenticationMode = loopback_none
credentialRef = null
subject = null
assuranceLevel = low
```

It receives the narrow deployment-configured scope set and must never be enabled for non-loopback or Tunnel exposure.

### 4.3 Query-token compatibility

```text
kind = shared_secret_query
authenticationMode = query_token
credentialRef = local HMAC reference
subject = null
assuranceLevel = shared_secret
```

The credential-bearing URL remains a secret and is excluded from context, logs, errors, audits, and resource summaries.

### 4.4 Bearer token

```text
kind = shared_secret_bearer
authenticationMode = bearer
credentialRef = local HMAC reference
subject = null
assuranceLevel = shared_secret
```

Bearer support does not imply ChatGPT Web manual static-Bearer configuration support.

### 4.5 OAuth 2.1 future mapping

```text
kind = oauth_subject
authenticationMode = oauth2
credentialRef = safe token/client reference when available
subject = validated OAuth subject
assuranceLevel = strong
```

OAuth scopes are mapped into the same internal V1 scope vocabulary. Phase 8 may add assurance metadata through a new schema version, but it must not create a parallel authorization path.

## 5. RequestContextV1

```ts
interface RequestContextV1 {
  schemaVersion: 1;
  requestId: string;
  transportKind: "stdio" | "streamable_http";
  transportSessionId: string;
  identity: RequestIdentityV1;
  workspaceId: string | null;
  runtimeProfileId: string;
  permissionProfileId: string;
  policyRevision: string;
  sessionGrantRevision: string;
  receivedAt: string;
}
```

### 5.1 Request ID

`requestId` is generated at the central request boundary. It is opaque, unique enough for local correlation, and safe to return in exact result metadata after Phase 2A establishes transport-aware identity.

### 5.2 Transport session ID

- Streamable HTTP uses the validated MCP session ID.
- STDIO receives a process-lifetime opaque session ID generated once at transport startup.
- The value is never accepted from a tool argument.
- A closed or expired transport session cannot mint new contexts.

### 5.3 Workspace binding

`workspaceId` is nullable only for operations that do not address a workspace, such as selected server diagnostics or opening a workspace.

Phase 2B introduces:

```text
workspaceKey
  stable local key derived from canonical root

workspaceId
  opaque handle bound to identity + transport session + workspaceKey
```

A `workspaceId` from one transport session cannot be used by another transport session even when both authenticate with the same static Token.

### 5.4 Profiles and revisions

`runtimeProfileId` identifies startup and Tool Surface configuration. `permissionProfileId` identifies the permission ceiling. They are separate fields.

`policyRevision` identifies the immutable compiled snapshot. `sessionGrantRevision` identifies the current grant state. The request is stale when either revision no longer matches the active state required for a side effect.

## 6. Context creation flow

```text
transport validation
  -> Host / Origin / authentication
  -> transport session lookup
  -> RequestIdentity mapping
  -> runtime profile selection
  -> permission profile selection
  -> immutable policy snapshot lookup
  -> current session grant lookup
  -> RequestContextV1 creation
  -> central tool dispatch
```

The context is created once and passed explicitly. Domain services must not reconstruct identity from global environment variables, request headers, saved profile files, or process state.

## 7. Lifecycle rules

### 7.1 Policy change

When hard policy, identity mapping, Permission Profile, or deployment capabilities change:

- a new immutable `policyRevision` is created;
- previous approval grants become invalid;
- new requests use the new revision;
- writes, Git mutations, Shell, Process, and Network operations recheck revision before the side effect;
- a stale request returns `POLICY_CONTEXT_STALE` and does not retry automatically with broader access.

### 7.2 Session close or expiry

Closing or expiring a transport session invalidates:

- all session-bound workspaces;
- all SessionGrants;
- all pending approvals;
- all not-yet-started high-risk operations.

Persistent process handling is implemented later, but the interface must allow Phase 4A to terminate, quarantine, or refuse further interaction with a process whose owning context is revoked.

### 7.3 Credential rotation

Credential rotation creates a new `credentialRef`. Existing transport sessions authenticated with the old credential are closed or marked revoked according to the authentication subsystem. No profile or grant is migrated automatically to the new credential identity unless an explicit administrative migration is later approved.

## 8. Central enforcement boundary

The server must construct context and enforce policy at the shared direct-tool/supertool dispatch boundary. A supertool alias uses the same registered target handler and same context as direct invocation. It cannot mint a replacement context or select a broader profile.

Tool handlers may request a resource descriptor and decision, but they cannot:

- add scopes;
- alter identity assurance;
- change the permission profile;
- ignore a stale revision;
- convert a refusal into approval-required;
- call a domain service through an unguarded production path.

## 9. Privacy and logging

Safe identity fields for audit and diagnostics are limited to:

- identity kind;
- authentication mode;
- bounded safe `credentialRef`;
- OAuth subject only when policy explicitly permits its audit representation;
- scope names;
- assurance level;
- transport session ID;
- request ID.

The following are forbidden:

- raw Tokens;
- Authorization and Cookie headers;
- complete credential URLs;
- OAuth refresh/access tokens;
- client secrets;
- browser session material;
- a synthetic human identity inferred from a shared Token.

## 10. Failure semantics

| Failure | Result |
|---|---|
| Invalid or missing HTTP authentication | Transport `401` |
| Invalid Host or Origin | Transport `403` |
| Missing or invalid MCP session | Existing bounded MCP session error |
| Context cannot be constructed safely | `POLICY_CONTEXT_INVALID` internal mapping to stable tool failure |
| Workspace belongs to another session/identity | `POLICY_DENIED` |
| Policy or grant revision changed | `POLICY_CONTEXT_STALE` |
| OAuth-only identity property requested before OAuth exists | `POLICY_DENIED` or capability unavailable, never fabricated |

`POLICY_CONTEXT_INVALID` is an internal typed cause. Public tool contracts expose the nearest stable approved failure without raw transport or credential details.

## 11. Compatibility constraints

Phase 2A preserves current STDIO, query-token, and Bearer connectivity. Identity mapping is additive and internal.

Phase 2B removes implicit default-workspace fallback from core services. A one-cycle compatibility layer may translate legacy calls only when it can bind them unambiguously to the current transport session and the configured default root. Ambiguous or cross-session resolution fails closed.

## 12. Tests required by this ADR

- deterministic mapping for every transport/authentication mode;
- no raw credential present in context serialization, errors, audit facts, or logs;
- same credential produces stable local `credentialRef`, while different installations produce different references;
- query and Bearer shared secrets do not produce a human subject;
- future OAuth maps into the same internal scopes and context shape;
- STDIO and HTTP receive distinct process/session identifiers;
- cross-session workspace use fails even with the same credential;
- profile or policy update invalidates grants and side-effecting stale contexts;
- direct and supertool calls receive the same identity and revision;
- Tool Surface changes do not change the policy decision for an otherwise identical direct operation;
- session close invalidates workspaces, grants, and pending approvals.

## 13. Consequences

Benefits:

- one identity model survives the transition to OAuth;
- static credentials are not misrepresented as human users;
- policy decisions and audits become transport-aware;
- workspace isolation has an explicit Phase 2B foundation;
- stale grants and profile updates have deterministic behavior.

Costs:

- server construction and dispatch must carry context explicitly;
- tests need identity/session fixtures;
- existing global workspace fallback must be removed in Phase 2B;
- static-token deployments retain limited identity assurance until Phase 8.

## 14. Security claims prohibited by this ADR

Before Phase 8, CodexPro must not claim:

- strong per-human owner isolation;
- revocable OAuth subject identity;
- independent users behind a shared Token;
- that transport authentication alone authorizes filesystem, Git, Shell, Process, or Network access.
