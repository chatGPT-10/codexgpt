## 2026-08-16 — STEP-492: Design OAuth cross-transport workspace capability successor

**Status:** Complete design/TDD step; runtime remains unchanged and Phase 0 stays blocked at A1.

**Goal:** Replace the invalid future assumption that a ChatGPT Web task retains one MCP transport with a security contract in which an explicitly opened configured-root capability can survive transport rotation for the same exact OAuth authorization, without restoring process-global/path-derived authority or hiding lookup failure with the default workspace.

**Decision:** Select a server-side random opaque registry shared only inside one `OAuthReadOnlyMcpRuntime`/deployment incarnation and explicitly injected into transport-created servers. Keep public `ws_<32hex>`, sliding TTL, explicit close, policy invalidation, native realpath/allowedRoots/PathGuard and non-oracular `WORKSPACE_NOT_FOUND`. The exact capability principal is deployment binding + incarnation + `ownerRef` + `clientRef` + resource + `grantId` + `grantRevision`; policy revision is a separate validity epoch. Transport session, access-token ID/fingerprint and refresh generation are deliberately excluded so ordinary MCP rotation/token refresh stay continuous. A new/revised grant intentionally requires a reopen. Successor v1 remains process-ephemeral: service/runtime restart invalidates old workspace handles.

**Adversarial review corrections:** Foreign-principal lookup/close is a side-effect-free miss; it must never revoke the legitimate record, avoiding a copied-handle DoS created by sharing the map. Registry ownership stays per OAuth runtime instance rather than module/process global, and two runtime instances cannot resolve each other's handles. Only configured-root records are shared; confirmed roots, task worktrees, process/change-set/approval/Git authority remain independently bound. Registry-level revocation events must fan out close/expiry/policy invalidation to live per-transport semantic/cache subscribers while transport close merely unsubscribes. Shared aggregation is count-bounded without evicting live handles: 64 active configured-root capabilities per exact principal and 256 per OAuth runtime; overflow uses the existing non-sensitive `WORKSPACE_OPEN_FAILED`. Theft of both an exact-grant bearer token and its handle remains the existing Phase 8 bearer limitation; no DPoP/mTLS claim is added.
